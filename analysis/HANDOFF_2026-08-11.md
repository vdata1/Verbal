## NEW: run the pinned engines natively, no docker

Docker's container-creation path was wedged all session — `docker create` timed out at 100 s while
`docker ps` / `docker info` / `docker images` answered instantly, daemon 28.1.1 healthy, disk 95%
but 96 G free. Stuck `docker run` clients accumulate and need `pkill`.

`docker save` is a **read** path and still worked, which is the way around it:

```
docker save verbal:latest -o /scratch/turcotte/verbal_img.tar
mkdir img_extract && tar -xf verbal_img.tar -C img_extract
# one layer holds all three:
tar -xf img_extract/blobs/sha256/a0e180ee5a9b... usr/local/bin/{node,bun,deno}
```

They run directly on the host. **Already extracted and kept at
`/scratch/turcotte/pinned_engines/usr/local/bin/{node,bun,deno}`** — versions match
`.engine-pins.json` (node v26.5.0 / bun 1.3.14 / deno 2.9.1). A native bun 1.4.0-canary also exists
at `/scratch/turcotte/verbal/engines/bun-linux-x64/bun`.

This makes probe/reduction work independent of docker and of the container-start cost. It does
**not** replace docker for full pipeline runs (those want the image's whole environment).

## Measurement discipline on this box — a live example

A single timing reading here is worth nothing. The same verbatim case measured **521 ms** on one
fresh-process run and **0.001 ms median over 25** in-process. That 521 ms was a scheduling stall at
loadavg 60–80 and nearly went into the triage as a surviving 111× penalty. Use the value oracle
where one exists, or repeat-measure in-process and report the median with the spread. The tight
3 153–3 428 ms spread on bun 1.3.14 is what a *real* cost looks like by contrast.
